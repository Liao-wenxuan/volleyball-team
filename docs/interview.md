## 1. AI 助手（本地 BYOK 直连 + 云端服务端代理，双轨）

**我做的**：一条链路两种跑法。本地模式：浏览器直连 OpenAI 兼容的 `/chat/completions`，SSE 流式解析，Key 存 localStorage；云端模式（r34 起）：Key 只存服务端 `team_settings.ai`，浏览器把 messages 发给自建的 `POST /api/ai/chat`，服务端带着 Key 请求服务商并把 SSE 流**原样透传**回去。前端解析逻辑一行没改，只是 fetch 的目标换了个地址。三个快捷任务（本周小结/阵容建议/队员点评）+ 自由问答，上下文自动注入全队名单、本周考勤、最近 30 条技能调整。

**为什么先是浏览器直连、后来又加代理**：
- 项目定位「本地优先」，大部分用户根本不部署后端，走代理 = 强制部署才有 AI。所以本地模式保留直连，Key 不经过任何中间方。
- 但上了云之后故事变了：服务器本来就存着 Key（换设备免重填），却还把明文 Key 随 `/api/auth/me` 下发给浏览器——等于「我存着钥匙还到处复印」。r34 把云端改成代理：Key 永不回传（接口返回 `••••••••••` 掩码占位），保存时前端原样交回掩码则服务端保留原值。
- 代价：自部署的服务器能看到 Key。但这个 Key 本来就存在它的数据库里，没有增加新的信任面；反而消掉了「Key 出现在浏览器内存/网络面板」的暴露面。

**面试官会追问**：
- 「流式怎么透传的？」→ 服务端用全局 fetch 请求上游（`stream: true`），拿到 `res.body`（Web ReadableStream）后循环 `reader.read()`，每个 chunk `res.write(Buffer.from(value))` 直写回客户端，Header 设 `text/event-stream`。前端 `res.body.getReader()` 按行切 `data:` 帧的解析代码零改动。
- 「用户点停止怎么不浪费钱？」→ 客户端断开时要把上游请求一起掐掉。这里踩过一个 Node 语义坑：我最初挂 `req.on('close')`，结果**请求体一读完就触发 close**（Node 18+ 的 IncomingMessage 语义），上游请求刚发出去就被 abort，全部 500。正确做法是挂 `res.on('close')` 且判断 `!res.writableEnded`——只有连接异常断开才 abort。
- 「上下文怎么控制？」→ 系统提示词注入全量结构化数据，对话历史只带最近 10 条。20 人队的数据量远小于上下文限制，不值得做检索。
- 「掩码会不会被绕过？」→ 掩码只做展示层判断，真正兜底是服务端：PUT /ai 收到掩码值就保留原 Key，掩码字符串永远不会被当成真 Key 存库。

**踩过的坑**：
- 保存 Key 后重渲染页面，`.reveal` 动画没刷新，面板一直 opacity:0。教训：任何 innerHTML 重渲染后必须重触发入场动画。
- Key 存在 `db.settings.ai`，normalizeDB 白名单没带回它，刷新就丢。教训：**每加一个持久化字段，blankDB 和 normalizeDB 必须成对改**，这个坑踩了三次。

## 2. 批量导入名单

**我做的**：一个粘贴框吃四种来源——Excel/腾讯文档复制（Tab 分隔）、CSV、群接龙文本（`1. 张三 主攻 188`）。表头识别、序号剥离、位置别名归一（接应二传→接应）、身高认 `188cm` 和 `1.85` 两种写法；号码重复、身高越界、缺姓名的行标红禁选，预览表逐行勾选后才建队。

**为什么做解析器而不是做个收集表单**：队长手上已经有现成名单（Excel 或群里接龙），表单意味着 18 个人每人填一遍、队长再催一遍。解析器把录入成本压到"复制粘贴一次"。工具应该迁就数据的现状，而不是要求数据迁就工具。

**面试官会追问**：
- 「表头怎么认？」→ 每个字段一组别名，至少命中 2 个字段才认定是表头行；单字别名（如「号」）要求全等，不然「5号」会被当成表头。
- 「脏数据怎么处理？」→ 分两档：能猜的（位置写"主攻手"）自动归一后给警告；不能猜的（号码重复）整行禁用。宁可少导入一行，不导入错的一行。
- 「号码重复为什么不是全局唯一？」→ **队里的真实规则是同性别内不重号，男队女队可以穿同一个号**（我们队男 4 号和女 4 号是两件球衣）。所以查重的键是「号码 + 性别」，不是号码。性别没填的人先归到同一组互相查——因为不知道就该按最严的算；预览里点出性别，警告会当场消失。这条规则最开始被我写成了全局唯一，是队长提出来才改的：**约束是业务给的，不是数据库给的，凭空收紧规则等于给用户制造错误。**

## 3. 阵型库与云端同步

**我做的**：战术板摆好 6 个角色位后「存当前」起名入库（上限 30 套），列表里改名（内联编辑）、用当前站位覆盖、删除；云端模式新增 `formation_saves` 表（复合主键 team_id+id 做租户隔离），`GET|PUT /api/formation/library` 整库同步，客户端 4 个变更点（存/删/改名/覆盖）挂钩推送。

**为什么整库替换而不是逐条 CRUD**：
- 30 套 × 6 坐标的 JSON 不到 20KB，整库推没有性能问题。
- 逐条 CRUD 要处理临时 id 对不上、离线冲突、操作顺序，为 20KB 数据写一套同步协议不划算。
- 服务端一个事务删旧写新，天然幂等；客户端失败就回拉全量，以服务器为准。
- 边界也想清楚了：这套方案在"库大到单次请求都放不下"时会失效，但 30 套上限的设计让它永远到不了那一天。**方案的错误边界是自己设计的上限**，这是有意的。

**为什么删掉了出厂预设（三套默认阵型）**：预设是我猜的"典型站位"，真实用户（队长本人）有自己的站位习惯，预设卡片占了列表一半却没人点。删掉后整个 presetEdits（预设改名/改位记录）字段连同白名单一起清掉，界面只剩用户自己存的东西。**功能做减法的判断标准：我作为"假想用户"加的功能，真实用户用不用？**

**面试官会追问**：
- 「内联改名有什么坑？」→ 点确认按钮时输入框先失焦，失焦回调把改名行重建了，click 就落空。解法：确认按钮 pointerdown 阶段 preventDefault 压住失焦，让 click 正常走到输入框被销毁之前。
- 「多设备同时改库怎么办？」→ last-write-wins 整库覆盖。单队长使用场景下没有并发写，不做 CRDT。

## 4. 移动端的文件选择（一个按钮换了三种写法才点得动）

**现象**：同一个「选择文件」按钮，电脑上一点就弹选择器，队长自己的安卓平板上点了**完全没反应**——没有报错、没有 toast，就是静悄悄。

**三代写法，逐代被现实否定**：

| 写法 | 结果 | 为什么 |
|---|---|---|
| `<input type="file" style="display:none">` + `input.click()` | 桌面能用，安卓 PWA 吞掉 | WebAPK 独立窗口里，非用户直接操作的程序化 click 会被拦 |
| 改成 `<label for="inputId">` 原生触发（不写 JS） | 备份导入好了，表格导入在平板上仍然没反应 | 依赖浏览器把点击 label 合成为「点击 input」，这层代理在桌面可靠、在安卓 PWA 上时灵时不灵 |
| **`<input>` 透明铺满按钮本体**（`position:absolute;inset:0;opacity:0`） | 两个入口都稳了 | 手指点到的**就是 input 本身**，不经过任何代理层，也没有可被拦的程序化 click |

**为什么最后这版能治本**：前两代都在赌「浏览器会替我把点击转发给 input」。转发链上有三处可能断：程序化 click 的信任标记、label 激活的合成事件、离屏或 1px 元素的命中测试。铺满之后链路长度变成 1，没有转发就没有可断的地方。

**代价说清楚**：input 必须跟着按钮一起重建，所以 `change` 监听要绑在弹窗打开时（原来绑在常驻 DOM 上的那份失效了）；选完文件要立刻 `input.value = ''`，否则同一个文件改完内容再选一次不触发 change。

**面试官会追问**：
- 「为什么不用 `accept` 过滤类型？」→ iPadOS 和部分安卓的文档选择器按 MIME/UTI 过滤，`.json`、`.xlsx` 经常认不出来，文件在选择器里是灰的点不动——比不弹更让人困惑。类型校验放在读文件之后做，错了给具体提示。
- 「怎么确认是环境问题而不是代码 bug？」→ 用 CDP 的 `DOM.setFileInputFiles` 直接给 input 塞文件，能跑通整条导入链路 → 代码没问题，断在「用户点到 input」这一步。再用 `document.elementFromPoint(按钮中心)` 查命中的是哪个元素，一眼看出点击被谁挡了。
- 「这类问题怎么提前发现？」→ 自己只在小屏模拟器里测是发现不了的（模拟器里 `click()` 照样有效）。得在真机的 PWA 里点一次。**验收标准要写清"在什么环境里算通过"**，否则"我这儿好使"会一路带到用户手上。

## 5. 多租户与角色模型（管理端 / 教练端 / 队员端）

**我做的**：三种角色三套入口。admin（只有我）用独立页面 `/admin` 管理多支球队：一键建队（队名+教练姓名 → 自动建 coach 账号+一次性密码）、账号管理（重置/禁用/启用）；coach 登录教练端管理自己的队；player 用手机页 `/m` 只读看自己（下次训练倒计时、出勤率、技能雷达、教练点评、近 5 次记录），唯一的写权限是「我要请假」。数据全部按 `team_id` 隔离。

**为什么三个角色拆三个入口而不是一个系统里切权限**：
- 管理端是纯桌面运营工具，一年用几次；教练端是平板高频录入；队员端是手机一屏只读。三类用户的设备、频率、心智完全不同，塞进一个界面只会互相拖累。
- 独立页面还天然做了权限的物理隔离：管理端不加载教练端任何逻辑，攻击面更小。
- 队员端单文件 `m.html` 由 Express 托管，自己的 manifest 和 sw（scope `/m/`），跟教练端的离线壳互不干扰。

**面试官会追问**：
- 「怎么防止队员越权？」→ 所有写接口 `requireRole('admin','coach')`，队员调用直接 403；`/api/me/summary` 按登录账号绑定的 `players.user_id` 取数，别人的数据一个字不出接口。请假接口也是最小授权：只能动「下一场还没开始」的训练，只能取消自己请的假，教练已标出勤后不能再动。
- 「Caddy 静态托管会不会吞掉这些页面？」→ 会，出过线上事故：`try_files` 兜底把 `/admin` 回成了教练端 index.html，而我当时的验证只看了 200 没看内容。修法：Express 显式路由 + Caddy `handle /admin*`、`/m*` 反代。教训：**部署验证必须断言响应内容，不能只看状态码。**

## 6. 同一浏览器两个标签登两个队（r29 会话隔离）

**我做的**：登录态四个 key（token/user/team/role）从 localStorage 改成 sessionStorage（每标签独立），localStorage 只留一份当「新开标签的默认身份」；本机数据缓存按 teamId 分桶（`xgy_volleyball_v2::<teamId>`），本地模式桶后缀为空。四个 key 必须整组同层读，不能混读。

**为什么这么拆**：事故现场是用户在公管队标签里加了队员，切到信工队标签一刷新，整个界面变成了公管队的数据——localStorage 按域共享，后登录的覆盖先登录的。分层之后：同浏览器两个标签各登各的队；退出登录只作用当前标签；关浏览器重开沿用最后登录的账号。

**面试官会追问**：
- 「sessionStorage 刷新会丢吗？」→ 不会，它按标签持久，只在标签关闭时清。会丢的是「关标签再开」的场景，这正是 localStorage 兜底（默认身份）存在的意义。
- 「数据缓存为什么也要分桶？」→ 只隔离登录态不够：内存里的 db 刷写会落到 localStorage，两个标签共享一个 key 照样互相覆盖。退出登录时还要把内存 db 切回「本机那份」，否则本地模式的编辑会写脏上一个队的缓存（串队事故二段）。

## 7. 服务端备份导入（r28 事务）与多端轮询同步（r34）

**备份导入我做的**：`POST /api/import` 一个事务吃整份 JSON，merge/replace 两种模式。merge 的认人规则和前端一致（姓名::号码），id 一律服务端重新生成（players.id 是全局主键），外键逐个翻译，孤儿记录丢弃，脏数据逐字段兜底——宁可变默认值不整包失败。replace 时按姓名+号码把队员账号绑定迁到新行，唯一索引防重复。

**为什么 id 要服务端重生成**：客户端备份里的 id 可能来自另一套库，直接用会和现有数据撞主键；且队内引用（考勤→队员、技能记录→队员）必须跟着换。服务端生成 + 翻译表（idMap）一次事务搞定，天然一致。

**轮询同步我做的**：`GET /api/sync/check` 只返回一个数字——本队所有数据表（队员/技能/场次/考勤/站位/阵型库/设置）的 MAX(时间戳)。教练端每 15 秒问一次，比自己上次看到的晚就整份拉回 + 重渲染；队员端同样轮询 summary，内容有变化才重绘。

**为什么轮询而不是 WebSocket/SSE**：单队数据的写入频率是「一天几十次」，15 秒轮询的成本约等于零，实现和维护成本也约等于零；WebSocket 要处理断线重连、心跳、多实例广播。**方案匹配负载，而不是匹配想象中的规模。**另一个关键细节：弹窗/抽屉打开时跳过刷新（`body.lock` 是现成信号），否则会把用户正在填的表单冲掉。

## 8. 测试体系（238 条单测 + 3 条 e2e）

**我做的**：`server/tests/` 下 11 个文件 199 条单测（vitest + supertest 风格直连 app），
覆盖鉴权、队员 CRUD、训练与考勤、技能事务、备份导入、阵型库、设置与 AI 掩码、管理端、同步口，
以及深度 health 的四项判定；根目录 `e2e/e2e.mjs` 三条 Playwright e2e（node:test 跑，不引第二个框架），
真 Edge headless → 真前端 → 真后端 → 真 SQLite，盖登录门禁、考勤持久化、阵型拖拽吸附三条主干；
`tests/pure.test.mjs` 和 `tests/courtcard.test.mjs` 再用 node:test 补 39 条前端纯函数单测（方案见下）。
三层合计 238 条单测，只配 3 条 e2e——金字塔不是凑数。

**为什么是这个时候决定写**：项目前两周靠 `tools/verify-*.mjs` 手工验证活着，真正的触发点有两个——
①鉴权和多租户是安全面，「改一行 SQL 忘带 team_id」这类事故手点是测不出来的，回归保护必须自动化；
②这个项目要作为面试项目，测试是工程纪律的直接证据。诚实地说两个动机都有，而且都是合理的。

**为什么测这几条**（按风险排序，不是按覆盖率凑数）：
- **鉴权边界**：过期/伪造 token、uid 不存在、停用账号的旧 token 立即失效（verifyUser 每次查库，这是设计承诺，必须测死）
- **幂等**：考勤是 UPSERT，同一人重复登记必须只有一条记录、最终状态 = 最后一次——这是接口文档承诺的行为
- **事务回滚**：批量改技能第二项指向不存在的球员 → 400，且第一项也不生效——事务的价值就在这条测试里被证明
- **跨队隔离**：每张表都有 team_id，但「有这个列」不等于「每条 SQL 都带了」；A 队的 token 摸 B 队的球员 id 必须处处 404
- **AI Key 掩码**：GET 永不回明文 + 前端交回掩码时保留原值——用 stub 的全局 fetch 抓服务端代理发出的 Authorization 头验证，因为掩码逻辑的 bug 只在「真实用 Key 的那一刻」暴露

**verify 脚本为什么不算测试**：`tools/verify-*.mjs` 是「跑一次、看输出、人眼判定」的一次性探针——
无断言、无隔离（跑完数据留在库里）、不进 CI、结果靠开发者自觉看。测试的定义是
**可重复的环境 + 自动断言 + 失败即红**。verify 在开发期探索阶段有价值，但它保护不了回归。
两者是分工不是替代：verify 帮我第一次把功能调通，测试保证它第二次还是通的。

**为可测试性做的最小改造**：`index.ts` 拆出 `app.ts` 的 `createApp()`，应用装配和端口监听分离，
测试不起端口直接注入 app；`db.ts` 本来就从 `DB_PATH` 环境变量建库，测试设成 `:memory:`，
配合 vitest 每文件独立 worker，天然做到每文件一个干净内存库 + beforeEach 清表。没有为测试改任何业务逻辑。

**测试抓到的真 bug**：请求体不是合法 JSON 时，body-parser 的解析错误绕过了 HttpError 分支，
直接进兜底返回 500——客户端错误不该是服务器内部错误。修法：errorMiddleware 识别
`entity.parse.failed` / `entity.too.large` 返回 400。这条测试现在写死在 auth.test.ts 里防回归。

**e2e 为什么只有 3 条**：金字塔配比。e2e 慢（3 条 11 秒 vs 199 条后端单测约 14 秒，前端 39 条纯函数仅 0.125 秒）、脆（依赖 DOM 结构和时序），
只值得盖「不跑就睡不着」的主干：登录、考勤、阵型。剩下的长尾组合全靠单测便宜地盖住。

**e2e 踩的两个坑**（都是真踩的）：
- **定位器抓错元素**：`#fxRoles [data-pos="oh1"]` 是侧栏图例文字，真正能拖的棋子是 `#fxCourt .fx-token[data-role="oh1"]`。抓错元素的隐蔽之处在于断言会以 NaN 形态「通过」——NaN 参与的比较恒为 false，`assert.ok(!(a&&b))` 形式的断言被 vacuous 通过。修法是先断言 `Number.isFinite`，永远先验证「值是数字」再验证「值对」。
- **浮点容差**：吸附后的坐标经「米 → 百分比字符串 → 米」换算回来有 1e-6 量级误差（6.25 变 6.249996），容差设 1e-6 必挂。设成网格的 2%（0.005m）才是对的——容差应该反映测量链路的真实精度，不是越小越严格。

**e2e 架子为什么用 node:test 不用 vitest**：根目录不为三条测试引入第二个测试框架；
node:test + playwright-core + 系统 Edge（executablePath，不下载 Chromium），
后端用 tsx 起在临时目录的独立 DB 上，测完全部清理。依赖为零增量。

**前端纯函数单测（39 条，vm 加载真实源码）**：补齐测试金字塔缺的前端那层。
`app.js` 末尾用 `if (typeof module === 'undefined')` 包住启动逻辑，并在后面加 `module.exports`
导出钩子——浏览器里 `module` 恒为 undefined，整段是死代码，启动行为零改动。
`tests/load-app.mjs` 用 `vm` 加最小 DOM 桩加载真实 `app.js`，跳过启动、导出 27 个纯函数，
测的是仓库里那份生产源码本身，不是复制副本，也不用引构建链。覆盖工具与 HTML 转义、
日期与周跨月跨年、技能 0.5 步进与 0–10 夹取、数据规范化白名单、阵型 0.25m 吸附、
粘贴名单四类分隔符与单位解析。
第二份 `tests/courtcard.test.mjs` 补 9 条，锁死「导出图和屏幕战术板用的是同一套坐标换算」：
`courtPoint()` 的米→像素、`clampMeters()` 的越界夹取、`shortLabel()` 的短标去重。
`tests/load-courtcard.mjs` 里 `document.createElement` 故意抛错——纯函数测试要是不小心走进 canvas 绘制路径，立刻红。
这不是凑测试数：导出图坐标算错了，屏幕上看着对、发给队友的 PNG 是错的，**没有单元测试会替你发现这件事**。

**为什么用 vm 加载而不是抽独立模块**：抽模块要同时改 `index.html` 引用、SW 预缓存、
`build.mjs` 单文件内联、preload 四条发布路径，风险全在配置层；而 vm 钩子只加 16 行、
函数体和调用点零改动。取舍标准：**测试可测性的代价要看"改了几条发布链路"，不是看"加了多少代码"。**
写断言前先把真值打出来，抓到几个反直觉但正确的契约：`fxSnap(0.1)` 会被边界夹到 `0.3`、
`parseKey('2026-02-29')` 归一到 `2026-03-01`、`'188cm'` 直接喂 `normalizePlayer` 会变 `0`（导入链必须先走高度归一）。
踩过 vm 跨 realm 的原型坑：沙箱里 `new` 出来的对象带另一套原型，`deepStrictEqual` 判结构相同但引用不等，
统一用 JSON 往返压成当前 realm 再比，已写进测试注释和 README。

## 9. 线上全站僵死 54 分钟与可观测性补齐

**我做的**：线上整站 0 字节超时，是用户自己刷网页发现的，不是系统告警。验尸定位到
`/opt/vigil` 的 Docker build + 一个无限重启的容器（`vigil-dashboard-1`）造成内存压力，
journal 刷了 252 次 `Under memory pressure` 但没有 OOM-killer——内存被慢慢吃光、进程没死、请求全卡住。
据此补齐三层可观测性：① `GET /api/health/deep` 深度检查（主库 `BEGIN IMMEDIATE` 取写锁读可用性、
磁盘 ≥512MB、系统可用内存 ≥128MB、最新备份 ≤36h，任一失败返 503；浅 health 契约不变）；
② 服务器 `watchdog.sh` + cron 每 2 分钟，连续 3 次超阈值才告警，日志附 Top RSS 进程快照，**只告警不自动杀**；
③ GitHub Actions `monitor.yml` 每 15 分钟从境外探测 health（连试两次、20s 超时）+ 首页校验 `<title`，
防反代把错误页当 200，失败自动开/复用 issue、恢复自动关闭。部署配置（Caddyfile / 部署脚本 / 看门狗）脱敏入库。

**为什么是这三层，且都不自动重启**：
- 浅 health 轻量给 Caddy/探活高频调用，deep 才做重 IO 检查——分层避免健康检查的 IO 拖垮正常请求。
- 看门狗只告警不杀：误杀线上比晚几分钟发现贵得多；而且整机僵死时看门狗自己也会停，所以外部探活才是最后一道。
- 不自动重启：自动重启会掩盖根因（上次就是容器无限重启把内存吃爆），重启循环本身还能造成二次事故。
- 诚实边界：GitHub cron 会排队、仓库连续 60 天无活动自动暂停；三者都不是分钟级监控，也不发短信/邮件。

**面试官会追问**：
- 「深度检查不会写脏数据吧？」→ `BEGIN IMMEDIATE` 立刻 `ROLLBACK`，零业务写入；查磁盘用 `df`、
  查内存用 `/proc/meminfo`、查备份用读最近一次备份文件 mtime。浅 health 只回 `{ok,name,time}`，部署脚本和 Caddy 都靠它。
- 「为什么用 `BEGIN IMMEDIATE` 而不是普通 SELECT？」→ 普通 SELECT 只验证"能读"，拿不到写锁就可能漏掉
  WAL 写锁争用导致的"读得到写不进"；IMMEDIATE 才真正验证写路径可用，且立刻回滚不影响并发。
- 「外部探活为什么既要 health 又要首页 `<title>`？」→ 反代能把 502 页面当 200 返回（Caddy `try_files`
  吞 `/admin` 的事故就是只看状态码踩的），所以既要 health 的真实 HTTP 码（连试两次防抖动）又要首页内容断言；
  探活本身也要防止"假阴性"。
- 「3 次阈值才告警会不会漏真故障？」→ 单次抖动（GC、瞬时高峰）不该触发，连续 3 次（6 分钟窗口）才说明
  真有持续压力；阈值保守是要压误报率，因为误报比晚发现更耗信任。

**踩过的坑**：
- "告警链路演练真跑过才敢说"：用不可达地址触发后自动创建了 issue #1（写明 `health HTTP 000` + 探测点 +
  run 链接），恢复正常地址后自动评论"已恢复"并关闭，演练 issue 标注"非真实故障"。否则"应该能告警"等于没验证。
- Git Bash 的 `/proc/meminfo` 没有 `MemAvailable` 字段，看门狗算术拿到空值会误判 0MB 告警——
  加了数字校验跳过，不会把"读不到"当成"内存耗尽"。
- 54 分钟的洞本质是"运维配置当装饰"——烟雾报警器挂墙上但没电池。

## 10. 性能优化：用数据推翻直觉

**我做的**：第二轮性能优化不靠猜。先量线上真实响应头：四个启动资源 gzip 38.9 / 79.8 / 48.0 / 16.0KB ≈ 183KB，
但每个请求 TTFB ≈ 0.9s（跨境 + 代理链路），且排球站点一个 Cache-Control 都没有（隔壁 csp 站点配了 immutable）。
三处改动：① Caddy 给版本化资源 `immutable` 一年、HTML/sw.js `no-cache`，条件请求 304 / 0B；
② SW 预缓存从 12 项 816KB 砍到 8 项 530KB（-35%），去掉首屏用不到的 3 张大图标和重复的 `'./'`
（和 `./index.html` 是同一份 HTML，白下 36.8KB）；③ head 加 `rel=preload` 让启动脚本与 CSS 并行。

**为什么 zlib 没换 zstd**：我本想用 zstd 压更狠，实测 `zstd(level 19)` 合计 **174.3KB 比 `gzip(level 9)` 172.1KB 还大**，
CSS 尤其明显（46.9 vs 42.8KB）。所以压缩算法一个字没动——**避免了一次"优化完反而更慢"的经典翻车**。
这一步的判断标准：优化前先量，数据不支持的直觉就砍掉。

**为什么动缓存头而不是动代码**：慢的是跨境链路的往返延迟（TTFB 1s），不是字节数。SW 缓存优先 + 启动脚本
preload 已经吃掉往返这块；二次加载 `transferSize = 0`。再省 60KB 对老用户无感。**优化要打在瓶颈上，不在边际上。**

**面试官会追问**：
- 「immutable 的风险？」→ 只有带 `?v=` 的版本化资源才 immutable，HTML/sw.js 反而 `no-cache`——sw.js
  必须每次能更新，否则发版用户永远拉不到新壳。发版靠版本号失效，不靠手动清缓存。
- 「preload 会不会造成重复下载？」→ 实测 6 个启动资源各只请求 1 次，preload 和后续执行是同一个请求；
  SW 安装 8 项、断网重载仍有内容。
- 「为什么不 minify/dist？」→ 项目无 dist 层（部署直接 cp 源码、Pages 用根目录、build.mjs 直接内联、
  SW 写死文件名、CI 只校验），引 minify 要同时改五处发布路径，为 36KB 不划算；而且源码注释（如"主题回跳根因"）
  是面试官爱追问的东西，可读性比 30KB 值钱。
- 「zstd 为什么反而大？」→ zstd 字典/帧头开销对小文件不友好，gzip 对文本久经优化；结论是"先量再定"，不是"新算法一定好"。

**踩过的坑**：
- 验收标准写"二次加载 `transferSize = 0`"而不是"页面变快了"——可量化才有意义；模糊的"感觉快了"测不出来。
- 单文件版（`file://`）要摘掉 preload 标签，否则指向不存在的外部脚本白发请求；`build.mjs` 同步处理。

## 11. CI 从「有」到「真门禁」+ 备份恢复演练

**我做的**：CI 一开始只跑不拦（push 同时触发 deploy）。改成 deploy 监听 `workflow_run` 且
`conclusion == success` 才部署，手动 `workflow_dispatch` 留作救急；根 `package.json` + 锁文件
（只装 playwright-core，不下载浏览器），e2e 跨平台（临时库改系统临时目录、浏览器 `E2E_CHROME` → Edge → Playwright Chromium）。
同时做备份恢复演练：取回备份副本核对 `integrity_check` + 各表行数，并用副本当 `DB_PATH` 起临时 API 验证可恢复。

**为什么备份演练会抓到真 bug**：服务器通用归档 `backup-db.sh` 遍历 `~/data` 下所有 `*.db` 只按 basename 命名 tar——
两个项目的库都叫 `app.db` 互相覆盖。解开当天 tar 是另一个项目的表（posts/products/wallets），不是排球队的
players/sessions。修：文件名带父目录前缀（`volleyball-app-…` / `csp-app-…`）+ 排除应用自己的滚动备份。
排球数据靠独立的 03:20 备份目录，没丢，但通用归档不可信。**演练的价值就在于"它可能真抓到 bug"。**

**面试官会追问**：
- 「CI 门禁会不会拖慢迭代？」→ 1 分多钟，且失败即红；真门禁的价值是"坏提交上不了服务器"——上次全站僵死期间若还乱推会更糟。
- 「演练为什么用副本起服务而不是只读校验？」→ 只读 `INTEGRITY_CHECK` 只证明"没坏"，不证明"能恢复"；
  用副本当 `DB_PATH` 起 API 才算验证可用性，两者差一步。
- 「为什么别人 clone 下来要能跑？」→ 公开面试项目，招聘方可能真的 `npm ci && npm test`；
  根 package.json 锁依赖 + e2e 跨平台是"零配置可复现"的承诺。

**踩过的坑**：
- 演练发现通用归档的"备份套娃"——把应用自己的滚动备份目录也打包了一遍；`find` 加 exclude 解决。
- README 被外部 Markdown 格式化器改坏（表格对齐、徽章链接被删、API 一览的 `GET|POST|PATCH|DELETE` 被当表格列拆开）——
  从此提交前 `git diff --numstat` 确认改动范围，被格式化器碰过就回退重放。
- 本机 `~/.ssh/config` 首行 BOM 让 SSH 报 `Bad configuration option`——删 BOM 修掉。

## 12. 最后一轮收尾：把「能用」变成「可接续」

**我做的**：这一轮不新增大功能，专治「项目别人接不走」。四件事：
① 阵型板导出 PNG（`courtcard.js`，零依赖手写 canvas，按需加载 + 单文件内联），把 Roadmap 最后一项清掉；
② 首屏三帧转 WebP（56.4KB → 32.9KB）但保留 PNG `onerror` 回退，且不用 `<picture>`（三帧靠 `:nth-child` 排动画延迟，换 picture 会让三张都变成 `nth-child(1)`）；
③ 补自研安全响应头，但**刻意不下发 CSP、不引 helmet**；
④ 补 `CHANGELOG.md` 讲清 `1.0.0` / `vN` / `r35.x` 三套编号的关系，并把写于「后端还在本地」年代的 `docs/上线清单.md` 对齐现实——已完成 / 明确不做 / 需外部条件三类分开写，路线 B（小程序）/ C / D / 桌面端整体标注放弃。

**为什么这一轮值得单列**：前几轮都在「加东西」，这一轮在「减歧义」。面试被问「你还有什么没做」时，
最有说服力的不是「都做完了」，而是能拿出一张清单说清哪几项刻意不做、哪几项卡在外部条件、哪几项有实测数字。
同理，「版本号真源是 `sw.js` 里那一行」这种事不写下来，下一个人就会去改 `package.json` 的 1.0.0，然后疑惑缓存为什么没失效。

**面试官会追问**：
- 「导出图为什么不复用 `card.js`？」→ 训练卡是「一段文字排版」，阵型图是「坐标系 + 网格 + 棋子」，尺寸和绘制模型都不同；共用反而要把两份都改成参数化。但风格一致：零依赖 canvas、UI 留在 `app.js`、模块按需加载、单文件版由 `build.mjs` 内联。
- 「WebP 为什么不直接把 PNG 删掉？」→ 删掉就没有回退面了。验证脚本跑三个场景：正常（只请求 3 个 WebP）、WebP 全 404（三张 PNG 回退仍加载且首屏正常结束）、单文件 `file://`（三帧都是内联 data URI，零外部请求）。**「优化」必须带着退化路径一起交付。**
- 「为什么不装 helmet？」→ 三端页面都是内联脚本，默认 CSP 会直接打白页面；真正需要的只是 5 个头 + HTTPS 下的 HSTS，自研 6 行就够，还顺手保证 404 / 错误响应也带头。装 helmet 得到的默认值恰好是这里要避开的那个。5 条测试把「不下发 CSP」这个决定锁死，防止后来者好心办坏事。
- 「后端改动为什么不 bump 版本号？」→ `vN` 是 SW 缓存名，只有前端静态资源变了才该变；后端 / 文档 / CI 改动不进预缓存，bump 只会白清一次用户缓存。这类变更按日期记在 CHANGELOG，不打版本标签。

**踩过的坑**：
- 导出图初版把「↑ 网」标画在场内，贴网棋子会压住；短标和全名相同时圆下重复写一遍；底部提示贴图例太近。三处都是**出图后肉眼看 PNG** 才发现，39 条纯函数测试一条也测不出视觉问题——所以补了 `preview/verify-courtcard.mjs` 真浏览器验证。纯函数测试和视觉验证是两层，不是互为替代。
- 验证脚本第一次被 `bootLoader` 和 `authGate` 挡住；静态服务器 `/sw.js` 返 404 还在控制台制造噪声，改成返回合法空 SW 才干净。
- 上线清单里「express-rate-limit」「helmet」两项差点照着装依赖：勘查后发现登录限流早就自研了（同 IP+用户名连错 5 次锁 15 分钟，29 条鉴权测试里有锁定/解锁用例），安全头自研 6 行也够。**照清单做之前先确认清单有没有过期**——这份清单写于后端还没部署时，连「双模式策略」的前提都已经不成立。
- **测试自己也会说谎**：最终全链路验证时 e2e 连挂两条（「初始应为未登记」、拖拽没变化），但业务代码一行没动。根因在架子：`e2e.mjs` 原来用 `npx ... shell:true` 起后端，`after()` 的 `kill()` 只杀到 Windows 的 cmd，真正跑 tsx 的 node 残留占住固定 8799；下一轮新后端 `EADDRINUSE` 退出，而 health 探测循环**没有断言失败就继续**，于是整轮测试静默跑在上一轮的旧库上（旧库里已有 present 考勤）。修法四件套：动态空闲端口、直接 `node + tsx CLI` 不经 shell、递归杀进程树、health 18s 未就绪直接红。这条比功能 bug 更值得讲：**测试连错了服务，给出的失败看起来完全像产品逻辑坏了**，排查方向会一路跑偏；「失败即红」不只要覆盖断言，还要覆盖环境就绪。

## 简历 bullet 候选（带数字，可直接抄）

- **可观测性闭环**：用 Node + Express + SQLite 独立部署的高校排球队工具，线上曾因容器无限重启整站僵死 54 分钟（靠人肉发现）。据此补齐三层可观测性——深度 health（DB 写锁/磁盘/内存/备份新鲜度）、每 2 分钟内存看门狗、GitHub Actions 外部探活自动开/关 issue，并脱敏入库部署配置；告警链路用不可达地址实跑验证，不靠"应该能告警"。
- **性能优化以数据为准**：测得跨境链路 TTFB≈0.9s 是瓶颈而非字节数，给版本化资源加 `immutable` 缓存头 + 启动脚本 preload，二次加载 `transferSize=0`；SW 预缓存瘦身 -35%；并实测推翻直觉（zstd 反比 gzip 大）避免了一次无效改动。
- **CI 真门禁 + 零配置复现**：把"CI 跑但不拦"改成 deploy 监听 CI 成功才触发，e2e 跨平台（`npm ci` 即跑），并将它做成公开面试项目的零配置可复现承诺；顺带用备份恢复演练真抓到通用归档按 basename 命名导致的跨项目覆盖 bug。
- **测试金字塔**：238 条单测（199 后端 vitest + 39 前端纯函数，node:test 用 vm 加载真实源码、零业务逻辑改动）+ 3 条 Playwright e2e，CI 门禁部署。
- **工程取舍**：本地优先单文件离线即用，又能切云端（Express + TypeScript + SQLite + JWT）多端同步；前端零框架依赖（原生 JS），PWA 缓存优先，单文件构建一键分发。
- **可交接性收尾**：Roadmap 清零（阵型导出 PNG，零依赖 canvas + 按需加载 + 单文件内联双路径验证）；首屏资源转 WebP 并保留零退化回退；自研安全响应头且明确不下发 CSP；补 CHANGELOG 版本体系与过期清单三分类，把「刻意不做」写成可辩护的决策而非遗漏。
