# 信工院排球队管理系统 · 面试问题全景

> 用途：把面试官可能从各个角度抛来的问题都先列出来，配「推荐答法 + 可能的追问 + 雷区」。
> 适用场景：前端 / 全栈实习岗。本项目是**第二项目**（区别于主项目 content-sharing-platform），定位是
> 「真实业务 + 全链路自己掌控 + 能把每个决策讲清楚」。
>
> 一句话定位（背下来）：
> **「一个面向高校排球队的管理工具，本地优先（单文件 HTML + localStorage 开箱即用），
> 可一键切到我用 Node/SQLite 搭的云端做多设备同步；核心模块是考勤、技能成长、战术摆阵，
> 还带一个导出成单 HTML 的队员档案和一套多球队管理后台。」**
>
> 讲法红线（来自长期记忆，务必遵守）：
> - **面试只讲前端**，后端架构我能讲，但落地承认「AI 辅助完成，我掌控需求、架构与验收」。
> - 代码里的业务约束（如号码同性别唯一）是**队长给的真实规则**，不是我拍脑袋的数据库约束。
> - 不吹"我从零手写了一个后端框架"这种越界的话。

信工院排球队管理系统  | 独立开发（前端为主，后端 AI 辅助）  | 2026.08 – 至今

## 1. 开场必问题（项目介绍类）

### Q1. 简单介绍一下你这个项目？
**答法**：用上面的「一句话定位」展开 30 秒版——谁用（高校排球队教练/队长）、解决什么痛点
（训练考勤靠微信群接龙、技能成长没记录、战术靠脑子记）、怎么解决（本地优先零部署 + 可选云端同步）、
技术栈（原生 JS 单文件 + PWA；后端 Node/Express/SQLite）。结尾一句收口：「它最特别的地方是
**本地和云端共用同一套界面，数据层可插拔**，而不是做两套应用。」

**追问**：「你为什么不做成 App？」→ 答：目标用户是教练的手机/平板，PWA 加「加到主屏」就能当 App 用，
零上架成本；且本地优先意味着没网络也能记考勤，比赛场馆常没信号，这是 App 反而难保证的。

**雷区**：不要一上来就堆技术名词。先讲业务，再讲技术。面试官要的是"你为什么做"，不是"你用了什么"。

### Q2. 为什么要做这个？灵感哪来的？
**答法**：真实需求驱动——身边排球队的训练管理全靠微信群接龙和 Excel，出勤统计、技能成长追踪、
战术布置都很原始。我想做一个"打开就用、教练不用学"的工具。**强调这是给自己/身边人用的真实产品，
不是练手 Demo**，所以需求收敛过程（见文档 2）和线上事故处理都是真实经历，经得起追问。

**追问**：「那为什么不做成 SaaS 卖给所有球队？」→ 答：当前定位就是单队自用 + 多队管理后台
（已做 /admin），没有做公开注册和计费，因为核心壁垒是"贴合排球业务"，不是"多租户基础设施"——
后者不值得我重造。

### Q3. 你这个项目里最大的技术挑战是什么？
**答法（挑一个你最熟的展开）**，推荐讲**双模式数据同步**：
本地优先意味着高频操作（考勤点格、拖阵型）必须先落本地再后台推云端，失败要回拉；
登录云端后服务器又变成唯一权威，整份覆盖本机。这两套语义在同一套 UI 里共存，
最难的不是接口，是**"哪些状态属于本地、哪些属于云端"的边界划分**，以及 12 个 mutation 点
怎么在不改动本地逻辑的前提下挂上云端钩子。

**备选挑战**：PWA 版本控制（SW 缓存导致用户拿不到新版本）、线上整站僵死 54 分钟的复盘
（见第 10 节，运维向面试官讲很加分）。

**雷区**：别说"最大的挑战是学某某框架"——这显得项目技术含量低。要讲**架构/边界/权衡**层面的难。

### Q4. 如果重来一次你会怎么改？
**答法**：诚实但积极。例子：
- 早点把"登录态按标签隔离"从一开始就设计进存储分层，而不是 v29 才补（同浏览器两个标签各登一个队的需求是后来才有的）。
- 后端如果用今天的认识，会更早抽 `verifyUser` 这种无 team 解析的函数，避免管理端自锁风险。
- 但核心决策（单文件本地优先、双模式可插拔）不会改，因为它们是由"教练零部署、场馆没信号"这个真实约束决定的，不是技术偏好。

**雷区**：不要为了显得"有反思"就否定自己的核心架构——那等于告诉面试官你之前的设计是错的。

## 2. 技术选型类

### Q5. 为什么用原生 JS，不用 Vue/React？（你本来就会 Vue 3）
**答法**：三个理由，按重要性排：
1. **交付形态决定**：产品要"双击 HTML 就能用"和"PWA 离线"，单文件 + 零构建依赖最稳；
   引框架要么打包要么 CDN，离线首屏和体积都吃亏。
2. **可控性**：我没有用框架的响应式系统，而是自己写了一个轻量 db 抽象 + 渲染调度，
   所有 mutation 点集中管理——这恰恰是为了后面挂云端钩子时能精确控制"哪些写要同步"。
   框架的响应式黑盒反而让我不好插这套逻辑。
3. **业务规模**：单队几十人，状态不复杂，框架的收益抵不过它的约束。

**追问**：「那你响应式怎么做的？」→ 答：db 对象统一入口，任何写操作走 `db.xxx()` 方法，
方法内部更新内存 + 落 localStorage +（云端模式）触发同步钩子；UI 通过显式的 `render()` 或
字段级更新重绘，不靠脏检查。

**追问**：「如果团队变大你会换框架吗？」→ 答：会评估，但当前规模下自写抽象够用且零依赖，
换框架是成本不是收益。**强调你不是"不会框架才不用"，而是"权衡后选择不用"**——
这正是面试官想听到的工程判断力。

**雷区**：别贬低框架，也别显得你只会原生。明确"我会 Vue，这里是不用"。

### Q6. 为什么是单文件 HTML？构建怎么做的？
**答法**：`build.mjs` 一个脚本把 `style.css` 和多个 `.js` 模块**内联**进 `index.html`，
产物就是一个文件，双击即用、能直接发 Pages、能当 PWA。开发时多文件拆分便于维护，
发布时内联便于分发——**开发体验和生产形态解耦**。

**追问**：「内联会不会让文件很大？」→ 答：当前单文件约 100KB（未压缩），gzip 后更小；
首屏用三帧 WebP 主源 + PNG 回退控制图片体积，没有引重型依赖。

**雷区**：说"内联是为了性能"不严谨——内联主要为了**分发便利和离线**，性能靠的是没重型依赖 + 图片策略。

### Q7. 后端为什么选 Express + better-sqlite3 + 原生 TS，不用 ORM？
**答法**：
- better-sqlite3 是**同步 API**，SQL 手写直观、事务语义清楚，单库单文件部署简单（Railway Volume 挂一个文件）。
- 业务 SQL 不复杂（考勤复合主键 UPSERT、导入事务），ORM 的抽象收益小，反而增加调试成本和体积。
- 原生 TS 不引装饰器框架，保持轻；zod 只做**入参校验**（边界防御），不作 ORM。

**雷区**：别把"不用 ORM"说成"ORM 不好"，说成"当前规模下 ORM 的抽象成本 > 收益"。

### Q8. PWA 为什么自己写 Service Worker，不用 Workbox？
**答法**：缓存语义很特殊——版本号是 `sw.js` 里的 `VERSION` 常量，是**唯一真源**，
`build.mjs` 用它在 HTML 引用和 SW 缓存名上同步刷 `?v=N`。Workbox 的自动哈希策略
对这种"单文件内联 + 手动版本"的发布模型反而碍事。自写 SW 让我精确控制**预缓存清单、
更新时机（skipWaiting 策略）、以及避免把 200 的 HTML 当图片缓存**这类坑。

**雷区**：说"Workbox 不好"是错的；说"我的发布模型特殊，通用方案反而增加心智负担"才对。

## 3. 架构设计类

### Q9. 双模式（本地/云端）到底怎么做的？为什么不是两套代码？
**答法**（核心，必须讲清楚）：
- **默认本地版**：所有数据走 localStorage（key `xgy_volleyball_v2`），UI 逻辑一行不为云端写。
- **云端版**：顶栏「云」按钮登录后切换。关键设计是 `cloud.js` 是一个**云端模块**，
  只在 12 个 mutation 点挂钩；`app.js` 的本地逻辑**一行没动**。
- 写策略分两类：增删改（队员/加练/删训练）**服务器先行取 id**；高频操作
  （考勤格、拖阵型防抖 600ms、技能批量、主题、模板）**本地先行 + 后台推送**，失败回拉以服务器为准。
- 边界划分原则：**"哪些状态必须服务端拍板"和"哪些可以先本地爽"是显式约定的**，不是混着写。

**追问**：「为什么高频操作敢本地先行？」→ 答：教练记考勤时如果每次点格都要等服务器响应，
场馆没信号就瘫痪了。本地先行保证"永远能记"，后台推送保证"最终同步"，冲突概率极低
（同一格不会两人同时改），且服务器是唯一权威，刷新即对齐。

**追问**：「12 个 mutation 点是怎么定的？」→ 答：把所有"会改数据的用户动作"列出来，
逐个判断它需要的是"先拿服务端 id"还是"先本地后推"，分类后即得到这 12 个钩子点。

**雷区**：别说"云端和本地共用代码所以简单"——共用 UI 不共用数据逻辑，数据层是**可插拔**的，
这正是设计难点，要讲出来。

### Q10. localStorage 和 SQLite 的数据模型怎么设计的？
**答法**：
- 前端：单一 `db` 对象，含 players / sessions（训练周）/ attendance / skills / formations / settings 等，
  落 localStorage 前做 `normalizeDB` 白名单清洗（防止旧版本字段污染）。
- 后端：多表，带 `team_id` 做多租户隔离；技能是 6 个 REAL 列（发球/一传/二传/扣球/拦网/防守）；
  考勤是 `(session_id, player_id)` 复合主键，用 UPSERT。
- **players.id 是全局主键，不是 team 内联合主键**——导入时一律 `newId` 重生成，避免跨队冲突。

**追问**：「为什么技能用 6 个列而不是一个 JSON/关联表？」→ 答：固定 6 项、查询总是"全队矩阵"，
列存最贴合使用模式，聚合和排序都简单；如果技能项会动态增减才值得拆表。

**雷区**：别把"前端单对象"和"后端关系表"说成同一套模型——它们是**同一业务的两层映射**，
同步时做的是语义对齐不是结构拷贝。

### Q11. 多租户怎么隔离？有没有越权风险？
**答法**：
- 所有业务表带 `team_id`；除登录/注册/导入这类无 team 的入口外，每个查询都带 `team_id` 过滤。
- `auth.ts` 抽了 `verifyUser`（无 team 解析）和带 team 的鉴权，避免管理端操作把自己锁死。
- 管理端 `/admin` 是独立页面 + 独立登录（`requireSysAdmin`），和教练端账号体系分开。

**追问**：「如果有人改前端把 team_id 改了能越权吗？」→ 答：team_id 不来自前端信任，
来自 JWT 解析出的用户所属 team；前端传的 team_id 只作参数，服务端以 token 为准重新确认归属，
越权查询在服务端就会被过滤掉。

**雷区**：别说"前端做了校验所以安全"——所有租户隔离必须在**服务端**兜底，前端校验只是体验。

### Q12. 前端模块怎么拆的？按需加载怎么做？
**答法**：核心是 `app.js`（主逻辑）+ `cloud.js`（云端模块）+ 按需模块
（`courtcard.js` 阵型导出 PNG、`playercard.js` 队员档案、`xlsx.js` 表格、`qr.js` 回执码等）。
按需模块在 `MODS` 映射注册，`build.mjs` 的 `lazyMods` 和 `ASSET_RE` 两处都要登记，漏一边就 404。
主包不含这些，用到时才动态载入——控制首屏体积。

**雷区**：说"用了动态 import"要能解释清楚两处登记的关系，否则像背的。

## 4. 数据层 / 离线类

### Q13. 离线优先怎么保证不丢数据？
**答法**：三层保障——
1. 每个 mutation 同步写 localStorage（同步 API，写完才返回，不会丢在内存里）。
2. 云端模式本地先行，保证"没网也能记"，联网后后台补推。
3. `normalizeDB` 在每次读时清洗，保证旧版本字段不会让新代码崩。

**追问**：「本地存储满了或被清怎么办？」→ 答：云端模式以服务器为权威，清了本地刷新即恢复；
本地模式提醒用户用"导入备份"导出 JSON。备份导入走 `merge`/`replace` 两种语义。

### Q14. 云端导入的 merge 和 replace 语义怎么设计？
**答法**（这是真被问到的好题）：
- **merge**：姓名::号码认人，只覆盖位置/年级/身高/技能；训练按"日期+开始时间"认同场，
  考勤整格覆盖；技能记录去重追加；模板/主题/阵型不动。
- **replace**：清空重写，且把队员账号绑定（`players.user_id`）迁到新行，避免账号失效。
- 两者都包在**一个事务**里，失败全回滚。

**雷区**：merge 不是"有就覆盖全部"——它刻意不动模板/主题/阵型，因为这些是"配置"不是"数据"，
混在一起覆盖会误删用户设置。

### Q15. 考勤只有 4 态（出勤/迟到/请假/缺席），迟到怎么算？
**答法**：迟到**计入出勤率但单独统计**——它和"出勤"是同一语义大类（人来了），
但单列出来让教练看纪律。下雨取消的训练不计入分母（不计入出勤率）。这是业务规则，不是技术选择。

## 5. PWA / 缓存类

### Q16. Service Worker 的版本控制和更新机制？
**答法**：
- `sw.js` 顶部 `VERSION` 是**唯一真源**；`build.mjs` 用它同步刷新 HTML 里资源的 `?v=N`
  和 SW 的缓存名 `xgy-pwa-${VERSION}`。
- 更新策略：新 SW 安装后**不立即接管**（避免正在用的页面被截断），下次导航才生效；
  但资源 URL 带 `?v=N`，所以新版本的资源名变了，旧缓存自然失效。
- **bump 规则**：只有进了预缓存的资源才 bump；后端/文档/CI 改动不 bump（否则白清用户缓存）。

**追问**：「用户一直不关页面会不会永远拿不到新版？」→ 答：SW 更新有激活时机，
且用户硬刷新（Ctrl+F5）会绕过；线上也提供 GitHub Pages 备用入口兜底。

**雷区**：把"版本号"说成在 package.json——那是发行版号，不随发版变；SW 的 VERSION 才是真源。

### Q17. 缓存策略？为什么 CSP 不能下发？
**答法**：
- 预缓存 shell（HTML/JS/CSS/首屏图），运行时用 cache-first 或 network-first 视资源类型而定。
- **CSP 永远不下发**：因为三端（主应用/管理端/队员卡）都依赖**内联脚本**，CSP 的
  `script-src` 限制会让内联脚本白屏。安全靠的是自研安全头（CORS/防盗链/限流），不靠 CSP。
- 教训：曾经想加 helmet/express-rate-limit，但三端内联脚本会白屏，且登录限流早已自研，
  所以**不装**这两个依赖（5 条测试锁死这个决策）。

**雷区**：别说"我没做安全"——要讲"我做了哪些、为什么不做的那部分"，显示你权衡过。

## 6. 登录 / 安全类

### Q18. 登录限流怎么做的？为什么自研不用 express-rate-limit？
**答法**：
- 按「IP + 用户名」统计连续失败，超阈值（如 5 次）锁 15 分钟，返回 429。
- 自研原因：① 上面说的，不想引 helmet/rate-limit 破坏内联脚本环境；② 限流要和服务端
  登录逻辑深度耦合（锁的是"这个假账号"，不影响其他账号），自研更可控。
- 实测：探测用的假账号被锁，换全新用户名仍是 401，说明限流**按账号隔离，不连累真实用户**。

**雷区**：别吹"我手写了比 rate-limit 更好的限流"——讲"为什么在这个项目里自研更合适"。

### Q19. JWT 怎么用的？token 存哪？
**答法**：
- 登录成功发 JWT（含 user/team/role），**存 sessionStorage 优先**（每标签一份、刷新保留），
  localStorage 只作"新开标签时的默认身份"。
- **四个 key（token/user/team/role）必须整组同层读**，不能混读——这样同浏览器两个标签
  可以各登一个队（localStorage 按域共享，单层存会互相覆盖）。
- 退出只作用当前标签，`logout` 后必须 `reloadLocal()` 把内存 db 切回本机那份。

**追问**：「为什么不用 localStorage 存 token？」→ 答：sessionStorage 标签页隔离，
避免"一个标签登录覆盖另一个标签身份"；且 XSS 拿不到跨标签的 token，缩小暴露面。

### Q20. 密码怎么存？
**答法**：bcryptjs 哈希，不存明文。登录用恒定时间比较，避免时序攻击。

## 7. 性能类

### Q21. 首屏慢怎么优化的？
**答法**：
- 首屏视觉是 SVG 战术板（矢量，零图片请求），不是位图排球。
- 关键图（首屏三帧）用 **WebP 主源 + PNG `onerror` 回退**，`<picture>` 标签按支持度选源，
  不破坏动画延迟。
- 按需模块懒加载，主包控制体积。
- 部署侧 Caddy 开 gzip，真机实测首页 39KB / 1.3 秒。

**雷区**：别把"curl 没带压缩测得 8 秒"当成真慢——那是测量方法错，不是性能问题
（这坑我们线上排查时真踩过，见第 10 节）。

### Q22. 阵型板拖拽性能怎么保证？
**答法**：拖拽过程只在内存更新坐标 + 视觉跟随，**松手才落库**；云端模式用 600ms 防抖合并推送，
避免每次 mousemove 都打请求。吸附按 0.25m 网格，松手结算，不是实时吸附。

## 8. 工程化 / 测试类

### Q23. 测试怎么做的？覆盖什么？
**答法**（数字要准）：
- **199 个后端单测**（11 个文件，node:test + 真 SQLite 临时库），覆盖路由、repo、鉴权、导入事务。
- **39 个纯函数单测**（2 个文件），覆盖数据归一、merge 语义、考勤计算等无副作用逻辑。
- **3 个 e2e**（真浏览器 Edge → 真前端 → 真后端 → 真 SQLite）：登录门禁、考勤落库、阵型拖拽推送。
- e2e 架子关键设计：动态空闲端口 + 不经 shell 直接起 tsx + `taskkill /T /F` 递归杀进程树
  + health 未就绪即红。固定端口 + shell 包装会让下一轮**静默跑在旧库上**，症状像业务 bug。

**追问**：「为什么纯函数单测和后端单测分开？」→ 答：纯函数无 IO，跑得快、能独立验证核心算法；
后端单测要起真 DB 验证 SQL 和事务，慢一些。分层让"改算法"和"改接口"的反馈速度不同。

**雷区**：数字说错（比如把 199 说成 200）会显得你没真做过。

### Q24. CI/CD 怎么搭的？
**答法**：
- GitHub Actions 两条：`ci.yml`（跑 test:all：后端单测 + 纯函数 + build + e2e），
  `deploy.yml` 监听 `ci.yml` 的 `workflow_run` 且 `conclusion==success` 才部署——**真门禁**，
  不是"跑但不拦"。
- 根 `package.json` + 锁文件让 clone 后 `npm ci && npm run test:all` 可复现。
- 部署到 Railway（自动重建），Pages 备用入口自动发布。

### Q25. build 内联脚本怎么工作的？
**答法**：`build.mjs` 读 `index.html` 模板，把 `<link>`/`<script src>` 引用的本地资源
内联成 `<style>`/`<script>`，同时根据 `sw.js` 的 `VERSION` 刷新资源引用的 `?v=N`，
输出单文件 `index.html`。开发时多文件，发布时单文件。

## 9. 部署运维类（面试官是资深/架构岗时很加分）

### Q26. 怎么部署的？
**答法**：
- 后端：Railway，Root Directory=`server`，Volume 挂 `/data` + `DB_PATH=/data/app.db`，
  环境变量 `JWT_SECRET`。已加 `nixpacks.toml` / `railway.json`（healthcheck `/api/health`）。
- 反代：Caddy（自动 HTTPS），站点 `vb.bscjs.top`。
- 备用：GitHub Pages 托管本地版（`liao-wenxuan.github.io/volleyball-team`），云端挂了还能用本地功能。
- 部署脚本 `deploy/deploy-volleyball.sh` 入库，确保新增 js 自动同步到服务器。

### Q27. 线上出过事故吗？怎么处理的？
**答法（这是最强的故事，讲透）**：出过两次真实事故——
1. **整站僵死 54 分钟**：一台监控容器（`/opt/vigil`）无限重启吃内存，把 API 进程挤死，
   journal 里 252 次 `Under memory pressure` 却没 OOM-killer。复盘后加了三层可观测性：
   `/api/health/deep`（DB 写锁/磁盘/内存/备份新鲜度）、服务器内存看门狗（每 2 分钟、
   连续 3 次才告警、只告警不杀）、GitHub Actions 外部探活自动开/关 issue。
2. **浏览器一直转（QUIC 陷阱）**：Caddy 下发 `Alt-Svc: h3` 让 Chrome 优先走 HTTP/3(UDP 443)，
   跨境 UDP 被丢 → 一直转或 `ERR_CONNECTION_RESET`。排查靠真浏览器对照实验
   （默认 0/4、禁用 QUIC 4/4），根治点是服务端关掉 HTTP/3 不再下发 Alt-Svc。

**追问**：「为什么 54 分钟才发现？」→ 答：原来没有外部探活，靠用户刷网页才发现。
这正是加 GitHub Actions 外部探活的直接动因——把"用户发现"变成"系统自动开 issue"。

**雷区**：讲事故要**坦承 + 有复盘动作**，不要粉饰。面试官看的是你"发现问题→定位→根治→防复发"
的闭环能力，不是你从不犯错。

### Q28. 监控怎么做的？
**答法**：`/api/health`（浅，进程活）和 `/api/health/deep`（深，DB 可写/磁盘/内存/备份新鲜度）；
内存看门狗；CI 外部探活自动建/关 issue；部署配置脱敏入库 `deploy/`。备份恢复演练
抓到过真 bug（tar 按 basename 命名两个项目的 `app.db` 互相覆盖），修成带父目录前缀。

## 10. 业务 / 产品类

### Q29. 需求是怎么收敛的？
**答法**：项目起点是"多学院通用管理系统"，但后来**收敛为"以排球为核心"**——
因为通用系统没有差异化，而"平板端战术模拟"这种贴合排球的场景才有价值。收敛后重点功能是
战术摆阵（拖角色位、0.25m 吸附、PNG 导出），比赛模块被砍掉（用户确认不需要）。
**强调"做减法"也是能力**：你能讲清楚"为什么不做"，比"做了很多"更显成熟。

### Q30. 战术模拟为什么是"静态摆阵"不是"动画回放"？
**答法**：用户明确要的是"手指拖 6 个角色位摆防守站位"，不是时间轴动画。
我一开始想加回放，用户说不需要——**需求以用户为准，不自己加戏**。这也是长期记忆里的协作红线：
"有不懂的先问，不要自作主张扩功能"。

### Q31. 队员端为什么改成"单文件 HTML 导出"而不是发账号？
**答法**：原来想给队员发账号（`/m`），但队员只想看自己的档案和请假，发账号意味着
账号体系 + 权限 + 登录成本。改成**教练导出一份全队 .html**，队员用"姓名+号码"进门，
请假走回执码（和分享逻辑一致）。零账号、零后端依赖、可微信直接发——更贴合队员的使用场景。

## 11. 行为 / 软素质类

### Q32. 遇到不会的技术你怎么处理？
**答法**：举例——比如 SQL 我本来不熟（真实背景），做后端时先用技术探针
（better-sqlite3 建表 + 事务 + 一个查询）排除未知，再正式写；不确定的 API 语义
（如 Node 的 `req.on('close')` vs `res.on('close')`）直接写最小复现验证，而不是猜。
**强调"先证伪再写代码"**。

### Q33. AI 辅助到你什么程度？
**答法（诚实，重要）**：
- 前端：我主导架构和所有决策，AI 帮我写样板代码、查 API 细节、跑测试，**我掌控每一行**。
- 后端：承认 AI 辅助完成度更高——我用 AI 搭了 Express/SQLite 骨架、写了大部分路由和测试，
  **但我定义需求、审查架构、写关键安全和同步逻辑、验收所有测试**。我不会把"AI 写的"说成"我手写"。
- 讲法原则：**不夸大、不隐瞒**。面试官问到后端细节我能答（因为验收过），但定位上诚实说是辅助。

**雷区**：① 别把 AI 辅助说成"我全手写"——被追问穿帮更糟。② 也别过度谦虚说"都是 AI 写的"——
那你这个项目的价值在哪？准确说是"我主导 + AI 提效"。
