# 训练卡 + 回执码 —— 原创产品方案

> 参考 `IOT-devstudio/iot-pillot` 只取两点灵感：**① 配色层级（深色底 + 单一高饱和强调色 + mono 英文小标签）；② "海报式 hero"这种信息密度很低的开场。**
> 除此之外不沿用它的任何东西：不做账号体系、不做 views/components/services 分层、不做"登录 → 仪表盘 → 实体列表"的 SaaS 骨架。
> 下面的场景、架构、数据流、模块划分、交互、业务逻辑全部是重新设计的。

---

## 一、创意概述

### 1.1 一句话

把「队伍管理系统」重新定义成 **「训练作品生成器」**：每次训练结束自动产出一张能自己传播的卡片，管理只是副产品。

### 1.2 为什么换切入点

市面产品（斑马邦）和参考项目共享同一个隐含前提：**这是一个"给人查数据"的工具**——登录、录入、看统计。这个前提决定了三件事：

1. 它只能停在队长手里（队员没有理由打开一个"管理工具"）
2. 它的传播系数 = 0（一个队长来，零个队员留）
3. 它的价值要等一学期才看得见（统计是滞后指标）

而队长的真实痛点不是"查看统计"，是 **"训练结束后 5 分钟内把这次训练记完，并且让队员知道"**。前者是查询，后者是**产出 + 分发**。

所以切入点从「以队伍/队员为原子单位」改成 **「以一次训练为原子单位」**：排它 → 记它 → 评它 → 产出它 → 发出去。系统做的每件事都围绕"这一次训练"。

### 1.3 三个原创概念

| 概念 | 一句话 | 原创点 |
|---|---|---|
| **Artifact-first（产物优先）** | 不是"数据存库等人来看"，而是"每次训练自动生成一个可转发产物" | 录入变成产物的副产品，而不是产物等录入完成 |
| **回执码（Receipt Code）** | 零服务端下的双向通道：队员操作压缩成 8+2 字符短码，微信回传，队长粘贴合并 | **用人当传输层**，闭环不经过任何服务器 |
| **阵容完整度（Lineup Integrity）** | 出勤率之外的新指标：按**位置**统计本周缺谁 | 输出可执行结论（"缺副攻 → 拦网配合练不了"），不是数字 |

## 二、具体实现方案

### 2.1 系统架构：Snapshot-First 四层

不按"前端分层"切，按 **"数据怎么流"** 切：

```
┌─ L1 Store（事实）      append-only 事件日志，只增不改
│    事件类型：session.create / session.cancel / att.set / skill.adjust / receipt.merge
│
├─ L2 Projection（视图）  启动时由事件重放出当前状态，业务代码只读它
│    players / weeks / skills / formations —— 就是现在的 db 结构
│
├─ L3 Artifact（产物）   把 Projection 的某个"切片"渲染成图片或链接
│    训练卡（一次训练）/ 档案卡（一名队员）/ 赛季卡（一学期）
│
└─ L4 Transport（传输）  出站：hash 链接（已做）　入站：回执码（新增）
```

**与参考项目的结构性差异**：参考项目是 `views → components → services → 后端数据库`，数据流是请求-响应、中心化、依赖网络。
这里是 **单向事件流 + 投影 + 产物**，出站和入站都不走网络，走**链接和人**。

### 2.2 数据流

```
队长操作 ──► Event(append) ──► Projection 重放 ──► 页面重渲染
                                     │
                                     ├──► Artifact 切片 ──► canvas ──► PNG（训练卡）
                                     │                                    │
                                     │                                    ▼ 微信
                                     │                              队员打开只读页
                                     │                                    │ 队员操作
                                     └──► 收件箱 ◄── Receipt Code ◄───────┘
                                           │
                                           └──► 新 Event（闭环）
```

### 2.3 数据模型

- 新增 key `xgy_events_v3`：事件日志 `[{id, at, type, payload}]`
- 保留 `xgy_volleyball_v2` 作为 **投影缓存**（启动时直接读，不用每次重放，保证首屏速度）
- 事件幂等：`receipt.merge` 带来源与 op id，重复粘贴不重复生效
- **不全量事件溯源**（见 3.1）：只在写入时"双写"一条事件（主写 db + 追加 event），零风险拿到事件历史

### 2.4 功能模块（按训练生命周期划分，不按数据实体）

| 模块 | 触发时机 | 做什么 | 与现状关系 |
|---|---|---|---|
| **Plan 排期** | 一周一次 | 模板生成下周三次训练 | 现有「训练模板」，入口弱化 |
| **Check-in 到场** | 训练现场 | 5 秒签到页 | **新增核心页** |
| **Grow 成长** | 训练后 | 批量调技能 | 现有「成长」 |
| **Artifact 产物** | 训练后 / 每周 | 训练卡 / 档案卡 / 赛季卡 | **新增** |
| **Broadcast 分发** | 随时 | 分享链接 + 回执收件箱 | **新增（分享页升级）** |

#### Check-in 页（交互上最大的原创点）

训练现场，队长掏手机：一页 10 个大头像，
**点一下 = 出勤，左滑 = 迟到，长按 = 请假，再点 = 撤销**。

现在这一步藏在「考勤页 → 选周 → 找日期 → 找格子」里，是推广时最容易劝退的地方。
把它提成独立入口，把"记一次考勤"从 ~30 秒压到 ~5 秒——这才是队长真正付费（愿意换工具）的那个动作。

### 2.5 三个产物（Artifact）

| 产物 | 内容 | 转发性 |
|---|---|---|
| **训练卡** | 战术板底图画本次到场阵型 + 缺席名单 + 到场率 + 本次进步榜 + 下次训练时间 | 队长发群（每周） |
| **档案卡** | 出勤环 + 六维雷达 + 里程碑（首次全勤 / 防守破 8） | **队员自己晒**（最强传播） |
| **赛季卡** | 出勤折线 + 阵容完整度热力 + 全队雷达对比 | 学期末总结 |

渲染：**手写 canvas**，不引 html2canvas。
理由：① 保持"零依赖 + 单文件双击可用"这条底线；② DOM 截图库在离屏渲染、字体加载、跨域图片上有各种坑，而卡片是固定版式，手绘反而更可控。
尺寸 750×1334（手机海报比例），导出 `canvas.toBlob` → 下载/长按保存。

### 2.6 回执码（技术细节）

**编码**
```
ops = [{t:'att.set', sid:'s_2026-11-03_tue', pid:'p3', state:'leave'}]
JSON → deflate-raw → Crockford base32（去掉 I/L/O/U 等易混字符）
→ 8 字符主体 + 2 字符 CRC → "K7M2-9XQD-3F"
```

**为什么 base32 而不是 base64**
微信输入框是真实传输介质：base64 里的 `+ / =` 会被自动换行/URL 转义破坏，大小写敏感对"手打一遍"的人是灾难。
Crockford base32 大小写不敏感、无符号、可双击整选。这是**由传输介质反推出来的编码选型**，不是随手选的。

**合并流程**
队长端「收件箱」：粘贴 → 校验 CRC → 解压 → **预览**（"张三 请假 11-07 周五 16:30"）→ 确认合并 → 追加事件 + 重放投影。
冲突处理：目标训练已被删除 / 状态已被改过 → 提示"已失效，请让队员重新生成"，不静默覆盖。

### 2.7 阵容完整度（业务逻辑创新）

```
完整度 = 本周「至少到过一次」的位置种类数 / 6（主攻/副攻/二传/接应/自由人…）
```

输出的是**结论**不是数字：

> 本周缺副攻 → 拦网配合练不了，建议改练一传串联

数据已经够了（队员表里就有 position 字段），不需要新采集任何东西。
这是排球特有的领域指标——参考项目的"在线/离线"是设备状态，这里的是**战术可执行性**。

## 三、关键决策与理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | **不做全量事件溯源**，只双写事件 | 现有 db 稳定、用户近期要写简历。重构全部读写路径的风险/收益比不划算；双写已经能拿到"赛季回顾 + 回执幂等"这两个真正需要的价值 |
| 2 | **产物用手写 canvas** 而非 DOM 截图库 | 零依赖、单文件、离线可控；卡片是固定版式，手绘比截图库更可控 |
| 3 | **双向通道用"人当传输层"** | 与已定决策「不搞服务器」一致；且这是一个能在面试里讲清楚的取舍（为什么不用 WebSocket：因为没有服务端，也不该有） |
| 4 | **新增 Check-in 页**而不是优化现有考勤表格 | 优化表单是在旧心智里打转；换入口才是降低门槛。推广的最大障碍就是"第一次试用太麻烦" |
| 5 | 分享页**只借鉴配色层级** | 参考项目我没取它的布局、信息架构、路由、组件划分——视觉语言（藏蓝 + 荧光绿 + mono 标签）是通用设计手法，不构成"照搬"；架构和业务逻辑全独立 |

## 四、相较参考项目的差异化

| 维度 | 参考项目（iot-pillot 类 SaaS） | 本方案 |
|---|---|---|
| 入口 | 登录 / 注册 | 无账号，链接即入口 |
| 架构 | 前端 + 后端 + 数据库，中心化 | 单机优先，快照广播，零服务端 |
| 数据流 | 请求-响应，双向靠网络 | 出站链接 / 入站回执码，双向靠人 |
| 代码分层 | views / components / services | Store / Projection / Artifact / Transport |
| 模块划分 | 按数据实体（设备、告警、用户） | 按训练生命周期（排期→到场→成长→产物→分发） |
| 产出物 | 页面内的图表 | 可转发的图片卡片 |
| 状态模型 | 当前状态记录 | 事件日志 + 投影（可回顾 / 可合并 / 可审计） |
| 领域指标 | 在线 / 离线 | 出勤率 + **阵容完整度**（位置维度，排球特有） |
| 交互范式 | 表单 + 表格 | 场景化（5 秒签到）+ 图形化产出 |

## 五、落地可行性

### 分期（每期独立可交付，随时可停）

| 期 | 内容 | 工作量 | 风险 |
|---|---|---|---|
| **P0** | Check-in 签到页 + 训练卡（canvas） | 2–3 天 | 低。收益最直接：推广物料 + 现场体验 |
| **P1** | 回执码（编码/解码 + 只读页操作 + 队长收件箱） | 2 天 | 中。要处理幂等与失效 |
| **P2** | 阵容完整度 + 赛季卡 | 1 天 | 低。纯计算 + 复用 canvas |

### 已知风险与对策

| 风险 | 对策 |
|---|---|
| canvas 中文换行需自己实现 | `measureText` 逐字断行，约 60 行，可控 |
| 微信里要能长按保存 | 用 `toBlob` 本地生成 PNG，不依赖任何在线服务 |
| 回执码过长不好粘贴 | 控制在 10 字符以内（8 主体 + 2 校验），分组显示 |
| **改版后 PWA 仍跑旧代码** | 每次改版必须升 `sw.js` VERSION（已吃过一次亏，写进流程） |

### 明确不做

全量事件溯源、多队伍、权限体系、真实服务端、WebSocket——前三个成本远高于收益，后两个与已定决策冲突。
