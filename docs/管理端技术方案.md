# 管理端技术方案（2026-11-02 与用户逐条确认）

## 一、需求基线（用户拍板，不再猜）

| 决策点 | 结论 |
|---|---|
| 定位 | 多球队运营平台，项目推广到各球队时由用户本人运营 |
| 使用者 | **只有用户本人**（admin = 系统管理员，全系统唯一） |
| 形态 | 独立页面独立入口（`/admin`），与教练端分开登录 |
| 角色模型 | admin=只有用户 → 管理端；coach=每队教练 → 现有界面；player=队员 → 手机页（后续） |
| 建队 | 一键建队：队名 + 教练姓名/用户名 → 球队 + coach 账号 + 一次性密码，模板/站位用系统默认 |
| 教练账号管理 | 重置密码、禁用、启用、改姓名，全在页面上做 |
| 队员账号 | 教练在自己队内开（现状不变，管理端不管到队员层） |
| 球队概览 | 每队：队员数、本周训练次数、最近活跃时间、出勤率 + 近 4 周出勤率小趋势图 |
| 停用策略 | 停用可恢复；停用后该队所有人无法登录但数据保留；**不提供删除** |
| 访问控制 | 非 admin 登录管理端直接拒绝；纯桌面，不做手机适配 |
| 教练端 | 本期原样不动 |

## 二、现状盘点（写方案前核实过的代码事实）

- `teams` 表只有 `id/name/created_at`，**没有 status 列** → 需迁移。
- `requireAuth`（auth.ts）验 JWT → 查 users → 按 `X-Team-Id` 或最早加入的队解析 membership。
  **不看 teams 状态**：停用球队目前拦不住登录后的请求。
- `routes/accounts.ts` 的账号管理全部带 `team_id` 作用域，且 admin 角色判定是「队内 membership」——跨队操作做不了，管理端需要自己的路由。
- `cli/account.ts` 的 `ensureTeam()` 已经实现「建队 + 默认模板 + 默认站位」，一键建队可以直接抽出来复用。
- 一次性密码生成 `genPassword()` 在 accounts.ts 和 account.ts 各有一份（8 位 / 10 位），本次抽成共享工具。
- 部署：GitHub Actions 纯 SSH → 服务器 `~/deploy-volleyball.sh`（脚本内容本机不可见，需上线时核实 STATIC_DIR/Caddy 细节，见 §七）。

## 三、数据库改动（一处）

```sql
ALTER TABLE teams ADD COLUMN status TEXT NOT NULL DEFAULT 'active';  -- 'active' | 'disabled'
```

- 放进 `db.ts` 迁移函数（新开 `migrateAdminV2()`），幂等判据：`columnNames('teams').includes('status')`。
- 只 ADD COLUMN 不重建：teams 被 7 张表外键引用，同 users 的教训，绝不 DROP。
- 角色模型零改动：`team_members.role` 的 CHECK 三值沿用；「系统管理员」判定 = 存在任意 `role='admin'` 的 membership。建队只发 coach，admin 权限不会自己长出来。

## 四、服务端改动

### 4.1 auth.ts 两处

1. **抽 `verifyUser(req)`**：只验 JWT + users.status，不解析球队。管理端路由专用——否则用户唯一 membership 的队被停用时，他自己也被锁在管理端外面（自锁事故）。
2. **requireAuth 补球队状态检查**：解析出 membership 后查 `teams.status`，`disabled` → `403 team_disabled`「球队已停用」。这是「停用队全员无法登录」的执行点（登录后的每个请求都过这里）。

登录接口（`/api/auth/login`）的 `payload()` 同样补：目标队 disabled → 403，停用队的教练连 token 都拿不到。

### 4.2 新路由 `routes/admin.ts`（挂 `/api/admin`，全部走 verifyUser + requireSysAdmin）

| 方法/路径 | 作用 | 说明 |
|---|---|---|
| `GET /api/admin/teams` | 球队概览 | 单条 SQL 聚合每队：队员数、本周训练次数（scheduled 未取消）、最近活跃（max(sessions.created_at, attendance.updated_at, skill_logs.at)）、出勤率、近 4 周趋势 |
| `POST /api/admin/teams` | 一键建队 | 事务：teams + team_settings（默认模板）+ formations（默认站位）+ coach 账号（must_change_pw=1）+ team_members；返回 `initialPassword` 只此一次 |
| `PATCH /api/admin/teams/:id` | 停用/恢复 | body `{status:'active'\|'disabled'}`；不能停用自己所在的队？——不做此限制，用户是唯一 admin 且管理端不依赖 team 状态 |
| `GET /api/admin/accounts?teamId=` | 某队账号列表 | 管理端弹层用，admin 账号行标灰禁操作 |
| `POST /api/admin/accounts/:id/reset-password` | 重置教练密码 | 跨队版本：按 user_id 查，目标含 admin 角色则 403（防动自己/防提权） |
| `PATCH /api/admin/accounts/:id` | 改姓名/停用/启用教练 | 同上，admin 账号一律 403 |

**requireSysAdmin 中间件**：verifyUser 后查 `EXISTS(SELECT 1 FROM team_members WHERE user_id=? AND role='admin')`，不满足 → 403。管理端权限以此为唯一判据。

**统计口径**（与前端一致）：
- 出勤率 = (present+late) / 全部四态记录；`cancelled` 的训练整体排除（因雨取消不计，沿用既有约定）。
- 近 4 周：以周一为界的 4 个自然周，每周一条 `{week, rate}`，无训练的周记 null（前端画空点）。

### 4.3 index.ts

- `app.use('/api/admin', adminRoutes)`（放在 `/api` 404 之前）。
- `GET /admin`（及 `/admin.html`）→ 返回 `server/public/admin.html`，**不依赖 STATIC_DIR**，随 server 构建产物一起走。

## 五、管理端前端（server/public/admin.html，单文件）

自包含 HTML+CSS+JS，不引外部依赖，风格沿用主前端视觉变量（同字体、同色板、桌面布局）。

```
┌ 登录屏：用户名+密码（调 /api/auth/login）→ role!=='admin' 直接拒绝并提示
│         mustChangePassword 时先强制改密（调 /api/auth/password）
└ 主界面（token 存 localStorage `xgy_admin_token`，401 时回登录屏）
   ├ 顶栏：系统名 + 用户名 + 退出
   ├ 球队概览：每队一张行卡（队名 | 状态徽标 | 四指标 + 4 周迷你趋势 SVG | 操作）
   │   操作：停用/恢复（二次确认）、管理教练账号（弹层）
   └ 教练账号弹层：列表 + 重置密码（弹一次性密码，明确「只显示这一次」）/ 停用 / 启用 / 改名
   └ 「+ 新建球队」按钮 → 弹层（队名/教练姓名/教练用户名）→ 成功后展示一次性密码
```

页面结构刻意薄：没有路由、没有状态管理，三个弹层 + 一个列表，原生 JS 一遍写完。

## 六、测试与上线

- 自动化脚本 `preview/srv/test-admin.sh`：建队 → coach 登录拿一次性密码 → 首登改密 → 概览数据核对 → 停用队 → coach 请求 403/login 403 → 恢复 → 教练重置密码 → 旧密码失效新一次性密码可登。管理端接口用 coach token 全部打一遍确认 403。
- 上线顺序：本地全绿 → push → Actions 自动部署 → `curl https://vb.bscjs.top/api/health` + `/admin` 200。
- 用户侧验收：浏览器开 `https://vb.bscjs.top/admin`，用 liao 登录，建一支测试队再停用。

## 七、上线时需核实的唯一风险点

`vb.bscjs.top` 的根路径前端现在由 Express（STATIC_DIR）还是 Caddy 静态目录直接托管，本机无法确认（部署脚本在服务器上）。
- 若是 Express 托管：`GET /admin` 直接生效，零额外配置。
- 若是 Caddy 静态优先：需要在 Caddyfile 加一条 `handle /admin*` 反代到 8787。**到服务器看一眼 deploy 脚本/Caddyfile 即可判定，不动别的。**
